2. 已确认的问题与仍未知的因素

代码确认：
  - 原前端 setInterval 每 3 秒发起轮询，单次认证 API 默认只等 10 秒，慢初始化会产生重叠请求。
  - 原扫码 handler 持有 session_manager guard 跨越远程预热和后续初始化。
    load_initial_session 中也有一个覆盖远程请求、实际未使用的 session guard。
  - 原四步预热使用客户端 60 秒超时并最多重试 3 次，无覆盖整体过程的总期限。
  - 多处失败分支仍可能把 Passport 认证成功当作完整初始化成功返回。
  - 原 record_failure 即使没有配置代理也可能翻转 fallen_back；execute_fallback 没有检查代理是否已禁用。
    已调度旧任务仍持有全局 fallback manager，因此禁用后旧失败也可能启动回退流程。
  - 原恢复任务只在 sleep 阶段监听取消；进行中的 probe 及成功后的旧配置发布没有同等保护。
  - 原回退/恢复热更新的一些入口只更新活跃账号，client_pool 与非活跃账号可能保留旧客户端。

不能据此断定用户 15:20 的日志唯一由哪一处造成。还需核对实际运行二进制、进程工作目录、
配置文件位置、是否已重启，以及旧进程是否仍在运行。
本项目读取相对路径 config/app.toml；直接编辑文件不等于更新运行进程中的配置。
通过设置页保存才会走现有热更新流程。直接编辑文件后需要重启对应服务/容器。
没有证据确认永久死锁、重复 STOKEN 的域冲突或百度风控是原故障根因。

3. A 的设计和实现

backend/src/server/handlers/auth.rs：LoginAttempts、qrcode_status、initialize_qrcode。
  每个生成的 sign 独立持有一个异步互斥锁，注册表锁只保护短时查找。
  同 sign 初始化期间返回 initializing；成功后复用脱敏结果；已确认用户缓存用于失败重试。
  基础会话保存成功后释放会话锁，再执行网络预热。保存失败可重试，不能伪报 ready。
  增加 /auth/qrcode/cancel；刷新、注销、切换账号使旧初始化 future 失效。
  尝试表最多 64 项，逻辑有效期 5 分钟；初始化 handler 总预算 110 秒。

frontend/src/stores/auth.ts、frontend/src/api/auth.ts：
  改为请求完成后延迟 3 秒再调度；generation ID 忽略过期结果。
  停止轮询时发送按 sign 的取消；注销/切换也使前端结果失效。
  初始化错误停止 loading 并交给原页面显示重试提示；轮询 API 超时改为 120 秒。
  二维码生成也有 generation 保护，较早生成的二维码不能覆盖较新的结果。
  Axios 传输错误转换为不含请求配置的普通 Error，避免控制台泄漏 sign 或提交的 Cookie。

backend/src/netdisk/client.rs：execute_warmup_request、bounded_warmup、warmup_and_get_cookies。
  保留原四步顺序、Cookie Jar、参数、重试和退避；四步单请求 15 秒（含响应体）。
  外层 45 秒覆盖验证、快捷路径、所有重试及退避。没有改变文件传输超时/stall 策略。
  日志保留 step、purpose、host/path、route、attempt、状态、耗时及错误类别，不保留 query。
  timeout 与确定的凭证失效分开描述；没有跳过预热或伪造 bdstoken。
  已确认的基础会话保留；未拿到关键 bdstoken 或 manager 初始化失败时不返回成功。

backend/src/auth/qrcode.rs、backend/src/auth/types.rs、backend/src/main.rs、
backend/src/server/handlers/accounts.rs、backend/src/server/state.rs：
  支持 initializing、取消路由、取消旧尝试；二维码 client clone 后立即释放共享读锁。

4. B 的设计和路由

配置：network.proxy.transfer_only: bool，serde 默认 false。
旧配置缺字段时兼容原模式；HTTP 与 SOCKS5 共用相同判定。
ProxyConfig::apply_control_to_builder 是控制入口；原 apply_to_builder 保留为数据/诊断入口。
transfer_only 开启时控制入口明确 no_proxy()，不会自动采用系统/环境代理。
无代理且未开启新选项的原有 reqwest 默认行为保留。

用途 -> 客户端 -> 路由：
  Passport/二维码/轮询/确认 -> QRCodeAuth -> control builder -> 直连。
  Cookie 导入验证 -> CookieLoginAuth -> control builder -> 直连。
  四步预热、用户信息、列表、搜索、文件管理、离线任务 -> NetdiskClient.client -> 直连。
  locatedownload/dlink/上传服务器获取/precreate/秒传/合并 -> 主 client 或临时 control client -> 直连。
  上传分片/重传 -> NetdiskClient.upload_chunk -> send_upload_chunk -> transfer_client -> 代理。
  下载整文件/Range/重定向/后续分片 -> DownloadEngine 共享下载 client -> 原代理。
  自动备份/加密上传/分享来源下载 -> 原 per-uid UploadManager/DownloadManager 调度链 -> 相同数据客户端。
  缩略图/预览等非任务控制请求仍使用控制客户端。
  代理测试与恢复 -> probe_proxy -> 强制指定代理的独立 client；错误 HTTP 状态不能算成功。
  配置保存 -> 原配置 API/PartialEq -> 更新各账号 managers、client_pool、备份与 monitor。

NetdiskClient 两个客户端共用该账号的 Cookie Jar，保持原 UA、TLS、重定向与认证策略。
控制直连失败不会增加/清除代理健康计数。数据请求继续沿用原回退、重试和恢复策略。
allow_fallback=false 时失败计数不能翻转实际路由标记；不擅自直连。
回退构造明确直连客户端；恢复时保留用户原始 transfer_only 选择。
代理热更新覆盖全部已注册账号，后续调度读取新快照；已发出请求不强行中止。
独立 UploadEngine 属旧的独立上传入口，当前生产任务通过 UploadManager/Scheduler；未重构该旧入口。

None 修复：
  on_user_config_change 规范化 Some(ProxyType::None) 为 None，并取消探测、重置状态。
  record_failure/execute_fallback 拒绝无代理或禁止回退的旧失败。
  probe 请求本身也监听取消；探测结果发布与用户改配置共用短时生命周期协调锁，
  并复查取消 token 和原配置，旧探测不能在禁用后恢复旧代理或再次输出失败循环。

新增字段复用原设置 API/持久化，无需单独改配置协议或增加页面。
设置页增加 Switch；无代理时禁用但保留选择。保存后重读配置，保留用户名/密码。
配置保存请求可包含 10 秒诊断，前端保存超时因此调整为 30 秒。
README、CHANGELOG、app.toml.example 已同步。

6. 使用、限制和回滚

在设置 -> 网络代理选择 HTTP 或 SOCKS5，填写地址和原有认证信息，打开“仅代理上传下载链路”，保存。
或在实际进程使用的 config/app.toml 的 [network.proxy] 中设置 transfer_only = true，再重启。
默认关闭。proxy_type = "none" 时不进行代理恢复探测；不要只改另一个工作目录中的同名配置文件。

真实手工验证尚未执行：
  1) 关闭开关确认原模式；开启并保存后扫码、浏览列表，核对脱敏 route 日志。
  2) 仅对操作者指定测试文件做上传/下载并比较 hash。
  3) 分别验证允许/禁止回退、代理恢复、none 和服务重启后的状态。
  4) 恢复原配置。若旧日志已经暴露登录 Cookie，应撤销相关会话。

百度是否要求链接生成和文件传输同一出口 IP 未验证；如遇此限制，关闭开关恢复原模式。
没有通过全局禁用代理、关闭 TLS、删除回退功能或改写认证参数绕过问题。
应用直连不排除操作系统透明代理/VPN；None 原有系统代理自动发现行为未全局重定义。
原“禁止回退但诊断不可用”的 UI 状态枚举沿用上游，内部实际路由不会因此切到直连。

无需破坏性 reset。首轮开发分支可按逆序 revert B、A；交付分支可 revert 单个中文修复提交。
仅需恢复原路由时关闭 transfer_only 即可；已有任务持久化、下载进度与账号隔离未迁移。

结论：代码层已消除已确认的轮询/长锁放大路径并给预热设总期限；严格文件数据代理路由有本地传输证据。
